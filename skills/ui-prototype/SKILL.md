# ui-prototype

把 grill-spec 写好的需求变成可点击的前端原型，放在 `docs/prototype/`，交给用户验收；通过后整理成 pi-forge `/forge-build` 能直接读取的样子。分六步：检查输入 → 选套件 → 搭工程 → 写页面 → 用户验收 → 交付。

## 轻量模式（quick）

`/ui-prototype quick <想看的页面描述>`（如 `quick 供应商列表和详情`）：还没有 PRD、只想先看几页时用。

- 跳过：第 0 步的输入检查、第 4 步，以及第 6 步的跳转页和交付检查。
- 照常做：第 1 步选套件、第 2 步搭工程、第 3 步只写描述里点名的页面（四种状态照样要有）、第 5 步截图自查和请用户验收。
- 页面的字段、操作、假数据从描述推出来，按套件规范定；描述含糊到连页面类型都定不了时，用 AskUserQuestion 问一次。自己定下的内容在第 5 步列出。
- 描述里没提角色时只留一个演示账号。第 5 步的修改意见只改原型（没有 PRD 可改）。
- 产物同样放在 `docs/prototype/`。在它的 README.md 标题下面写一行「模式：quick」，并把「需求以 PRD.md 为准」那句换成用户的描述原文。
- 用户通过后只打包 `app.html`（不删依赖），告诉用户：有了 PRD 再运行 `/ui-prototype`，会在原地补齐，不用重做。

## 0. 检查输入

- 需要 `docs/PRD.md` 和 `docs/ARCHITECTURE.md`，缺一个就停下，请用户先运行 `/grill-spec`。
- 从 PRD.md 的「页面」表读出页面清单（页面、原型文件、对应需求、路由），再读每个页面的规格（类型、字段、操作、状态、假数据）和「通用约定」。
- `docs/prototype/` 里已有本 skill 生成的原型（有 `package.json` 和 `README.md`）时是**修改模式**：沿用 README.md 里写的套件，在 `docs/prototype/` 里 `npm ci`，读源码后直接进第 4 步；用户调用时附带的意见作为第一轮修改。
- README.md 里写着「模式：quick」时，也按修改模式在原地补齐，不重建工程：照常做本步的检查；对照 PRD 页面表，已有的页面按页面规格改字段和假数据，没有的页面照第 3 步补上（角色、`review.json` 一起补）；然后照常做第 4–6 步。删掉 README 里「模式：quick」那一行，需求来源改回 PRD.md。
- `docs/prototype/` 里有别的东西（手写的原型等）时先问用户：覆盖 / 取消。

## 1. 选套件

- 套件在本 skill 目录的 `kits/<名字>/`，每套都有 `KIT.md`。只有一套就直接用；有多套时用 AskUserQuestion 让用户选，每个选项写一句这套的风格和适用场景。
- 下文 `<kit>` 指选中套件的绝对路径。先读完它的 `KIT.md`，再读 KIT.md 要求必读的文件（如设计规范）。

## 2. 搭工程

照 KIT.md「搭工程」在 `docs/prototype/` 里搭好，类型检查通过即可。预览服务器不会自己结束，留到第 5 步在后台启动。

## 3. 写页面

分三段：3a 搭骨架（自己做）→ 3b 写页面（页面多时分给子 agent 并行）→ 3c 合并（自己做）。

页面的通用要求（3b 不论谁写都照这个）：

- 照 KIT.md「写页面」实现：路由与「路由」列一致，结构、字段、操作照页面规格，假数据照「假数据」要求。
- 每个读数据的页面都要能显示四种状态：加载中、空数据、出错、无权限，切换方式写在 KIT.md 里（地址加 `?state=`）。
- 假数据前后矛盾（如页面规格要求的数据算出来和某条 AC 里的数字对不上）时，按页面规格做，第 5 步汇报时列出。
- PRD 没写清、又必须定下来的界面细节（如某个字段用下拉还是单选），按套件规范选一个，记下来，第 5 步汇报时列出。

### 3a 骨架

- 演示账号：PRD 有多个角色时，照 KIT.md 给每个角色一个演示账号，导航、按钮、数据都按当前角色显示；地址加 `?as=<账号>` 能直接以这个角色打开页面。
- 全部页面的空壳：套件有页面生成脚本时，用它给页面表里的每一页生成空壳（同时生成每个资源的接口层和假数据，并插好路由、导航）；脚本不生成的页面（概览、设置等）先手写一个能打开的空壳，路由也加上。
- 定下接口：照 PRD 改好每个资源的接口层——字段类型、筛选条件、提交字段、hooks 名，以及按角色的权限规则。之后 3b 只写页面，不再改接口。
- 骨架的其余部分照 KIT.md「改骨架」：外框文字、导航、命令面板、用户菜单。
- 写 `docs/prototype/review.json`，页面表每页一项：`{ "name": 页面名, "route": 主路由（参数换成假数据里真实的编号）, "as": 需要特定角色时的演示账号（不需要就不写） }`。第 5 步的截图和给用户的表都从它来；之后页面有增减时同步改。
- 类型检查和规范检查都通过，再往下。

### 3b 页面

- 页面少于 4 个：自己逐页写。
- 页面有 4 个或更多：用 Agent 工具分给子 agent 并行写，同时最多 4 个，有子 agent 回报了再派下一个。同一资源的几页（列表、详情、表单）交给同一个子 agent，因为它们共用一个假数据文件。给每个子 agent 的任务照下面写：

```
在 <项目>/docs/prototype/ 里写原型页面：{页面名列表}。
- 需求：{这几页在 PRD 里的页面规格原文，连同它引用的需求和验收标准}
- 规范：先读 docs/prototype/DESIGN.md；写法照样板 {样板路径}；套件说明 {KIT.md 路径}「写页面」一节
- 要改的文件：{页面文件路径}；假数据 src/mocks/{资源}.ts
- 只改上面这些文件。接口类型、公共组件、路由、导航、外框要改时不要自己动，写进回报
- 要求：四种状态（?state=loading / empty / error / forbidden）；{角色要求，如 只有管理员能看，用 ?as=lixiang 验证}；TODO(prd) 全部填完
- 做完在 docs/prototype/ 里运行 npm run typecheck，只管自己文件里的报错
- 回报：改了哪些文件；类型检查结果；需要主 agent 改的地方；自己定下的界面细节；发现的 PRD 矛盾
```

### 3c 合并

- 处理子 agent 回报里交给自己的改动（接口类型、公共组件、骨架），改完把受影响的页面一起调好。
- 全量跑类型检查和规范检查，并确认页面里没有剩下 `TODO(prd)`；都通过才进入下一步。
- 把各子 agent 定下的界面细节和发现的 PRD 矛盾合并起来，第 5 步一起汇报。

## 4. 填写前端技术栈

把 `docs/ARCHITECTURE.md` 的「3. 前端」整节内容换成 KIT.md「技术栈与版本」里的那一段（grill-spec 在那里留的是「由 ui-prototype 负责」）。其他节里如果还有交给 ui-prototype 的占位（如「前端的测试与检查由 ui-prototype 填写」），删掉那一行，前端的检查已经写在第 3 节；其余内容不动。

## 5. 用户验收

先自查，再交给用户：

1. 在后台启动预览（地址以命令打印的为准），照 KIT.md 截图：每页的正常状态和四种 `?state=` 各一张，总览在 `docs/prototype/.shots/index.html`。套件没有截图命令、或本机没有浏览器（命令会提示并跳过）时，跳过 1–3 步。
2. 逐张看截图（用 Read 打开 PNG），对照这张清单记下问题：文字溢出或截断；错位、对不齐；大块空白；一屏出现两个蓝色主按钮；空状态、出错状态没接上（还是正常页面，或一片空白）；命令输出里列出的页面报错。
3. 按清单改完，再截一次确认。
4. 给用户一张表，从 `review.json` 生成：每个页面一行，列出页面名、预览地址、四种状态的地址；页面需要特定角色才能看时，地址里带上 `?as=<账号>`。表后加一行「总览：docs/prototype/.shots/index.html」（跳过截图时不写）。再附上这一轮自己定下的界面细节，以及发现的 PRD 前后矛盾。
- 用 AskUserQuestion 问「通过，生成交付文件」还是「需要修改」（用户可以在 Other 里直接写意见）。
- 修改意见分两种：
  - **只动界面**（布局、文案、交互、假数据）：直接改原型。
  - **动了需求**（增删功能、改规则、改字段、增删页面）：原型和 `docs/PRD.md`、`docs/PRD-HUMAN.md` 一起改。PRD.md 保持 pi-forge 格式：需求标题带 `REQ-xxx`，验收标准每条一行 `- ACn Given … When … Then …`，页面表四列 `页面 | 原型文件 | 对应需求 | 路由`。已有编号不重排；新需求用下一个编号；删掉的需求整节删掉，并从页面表里去掉。改完列出改了哪些需求、验收标准和页面。
- 改完重新跑检查、重新截图自查，再请用户看，直到用户选「通过」。

## 6. 交付

1. 套件的类型检查、规范检查通过；按 KIT.md 打包出 `docs/prototype/app.html`。
2. 为页面表的每一行写一个跳转页，路径就是「原型文件」列，内容照下面的模板。
   - 路由带参数（如 `/queries/:id/edit`）时，用假数据里一个真实的编号。
   - 「路由」一格写了多个（用「、」隔开）时，跳到第一个，其余写在「其他路由」一行。
   - 页面需要特定角色才能看时，跳转地址带上 `?as=<账号>`，并写「演示身份」一行。
3. 删掉 `docs/prototype/node_modules/`、截图目录 `.shots/` 和打包的中间目录。pi-forge 读取原型目录时不看 `.gitignore`，超过 500 个文件或 30 MB 会直接报错。
4. 在项目根目录运行 `node <本 skill 目录>/scripts/check-export.mjs`，全部通过才算完成；不通过就按提示改，再跑一次。
5. 汇报，不超过 6 行：页面数、原型目录的文件数和大小、自己定下的界面细节、PRD 的改动（没有就不写），以及下一步：在 pi-forge 里运行 `/forge-build`。

跳转页模板（`{…}` 换成实际内容，源码路径相对 `docs/prototype/`；「其他路由」「演示身份」两行没有就删掉）：

```html
<!doctype html>
<html lang="zh-CN">
<head><meta charset="utf-8"><title>{页面名} · 原型</title></head>
<body>
<!--
  原型页面：{页面名}（{对应需求}）
  可点击：app.html#{路由}；四种状态在后面加 ?state=loading / empty / error / forbidden（已有 ? 时用 &state=）
  源码：{页面源码路径}
  其他路由：{如 /queries/:id/edit → app.html#/queries/12/edit}
  演示身份：{账号}（{角色}），其他身份把 ?as= 换成别的账号
-->
<script>location.replace('app.html#{路由}');</script>
</body>
</html>
```

## 新增套件

在 `kits/<名字>/` 下放这套 UI 的规范、样式、组件，再写一个 `KIT.md`，至少包含这几节（可以参照 `kits/strata/KIT.md`）：

1. **技术栈与版本**：一段能原样填进 ARCHITECTURE.md「3. 前端」的文字，包括前端的检查命令。
2. **搭工程**：在 `docs/prototype/` 里搭起能预览的工程的步骤。`DESIGN.md`（组件与用法）和 `theme.css`（设计 token）必须放在 `docs/prototype/` 根目录，pi-forge 开始前会检查。
3. **写页面**：页面样板在哪、数据和假数据怎么放、四种状态怎么用 `?state=` 切换、多个角色怎么用 `?as=<账号>` 切换（跳转页依赖这两个地址参数）。
4. **命令**：预览、类型检查、规范检查、打包成单文件 `app.html`（hash 路由，双击可开）、删除依赖；最好再有截图命令（读 `review.json`，输出 `.shots/index.html`），没有时第 5 步跳过截图自查。
