# grill-spec

把用户的项目想法变成三份文档：`docs/PRD.md`（需求，pi-forge 的输入格式）、`docs/PRD-HUMAN.md`（给人看的精简版）和 `docs/ARCHITECTURE.md`（技术栈）。分四步：拷问 → 确认共识 → 技术选型 → 写文档。每一步等用户回答后再往下走。文档写完就结束，不写代码、不搭原型；原型由下一步的 `/ui-prototype` 做。

## 0. 开始

- 用户调用时附带了想法，就以它为起点；没有就请用户用一段话描述：想做什么、给谁用、为什么现在做。
- 先自己收集**事实**。当前目录如果是已有项目，读 README、`docs/`、主要代码，了解已有功能、技术栈和约束；`docs/PRD.md` 或 `docs/ARCHITECTURE.md` 已存在时读进来作为输入。能查到的事实不问用户。

## 1. 拷问

把要定的事情看成一棵**决策树**：每个决定下面挂着依赖它的决定。一轮一轮地问：

- 每轮只问**前沿**：前提都已定下、现在就能回答的决定。依赖本轮其他问题答案的，留到下一轮。
- 用 AskUserQuestion 提问，每轮最多 4 题。每题 2–4 个选项，推荐项放第一个、label 末尾加「（推荐）」，description 写清这个选项意味着什么、代价是什么。用户总可以选 Other 自己写。没有 AskUserQuestion 时（如非交互模式），用编号文字列出同样的题目和选项，请用户按「1A 2B」回复。
- 只问**决定**，不问事实。事实自己查；查不到又影响决定的，写进选项（"日活过万选 A，否则选 B"）。
- 每轮提问前用 1–3 行说清上一轮定下了什么、因此冒出了哪些新问题。
- 回答模糊（Other 里写"看情况""都行"）的，下一轮追问到能落地；用户说"你定"的，采用推荐项并记为**假设**。
- 新回答推翻了之前的决定时，指出受影响的已定事项，重新问它们。

要覆盖的分支（大致按这个顺序，按依赖关系调整；与项目无关的分支说一句后跳过）：

1. **问题与目标**：解决谁的什么问题，怎么算成功（可度量的指标）。
2. **用户与角色**：有哪些角色，各自能看什么、做什么。
3. **范围**：本期做什么，明确不做什么。
4. **核心流程**：主流程的每一步，以及异常、失败、取消、空数据时怎样。
5. **页面**：有哪些页面，每页给谁用、放什么、能做哪些操作，从哪里进入。
6. **数据**：有哪些实体、关键字段、实体间关系、状态怎么流转。
7. **业务规则**：校验、计算、审批、通知、导入导出、第三方集成。
8. **非功能**：数据量与并发、性能、安全与合规、审计日志、可用性。
9. **约束**：上线时间、团队熟悉的语言和技术、预算、部署环境（公有云 / 内网 / 指定厂商）、必须用或不能用的技术与服务。第 3 步的选型靠它，必须问到。

所有分支都走过、没有任何事是悄悄假定的，拷问才结束。

## 2. 确认共识

输出一份不超过一屏的摘要：

- 一句话定位
- 已定决策（按上面的分支分组）
- 假设（逐条列出，用户可推翻）
- 明确不做

再用 AskUserQuestion 问「确认，进入选型」还是「需要修改」。要修改就回到第 1 步问相关问题，然后重新确认。

## 3. 技术选型

- **前端不在这里选**：由 `/ui-prototype` 按它选定的 UI 套件填写，ARCHITECTURE.md 的前端一节只写「由 ui-prototype 负责」。
- 后端给 2–3 套完整组合，每套覆盖 ARCHITECTURE.md 要写的各节：语言与框架、数据库与访问方式（含迁移）、认证方式、需要时的缓存 / 队列 / 文件存储、测试与检查工具、运行与部署方式。用户不在乎的项可以定为「由架构师定」。
- 每套方案都从第 1 步的结论出发说明：为什么适合（对应哪些需求和约束）、优点、代价与风险、运维复杂度、对团队技能的要求。先给一张对比表，再每套写几行，标出推荐方案和理由。
- 不为凑数给明显不合适的方案；只有一种合理选择时直接说明，请用户确认。
- 写具体版本号前先查当前稳定版（用可用的文档或搜索工具）；查不到就只写大版本并标「待确认」。
- 用 AskUserQuestion 让用户选。用户想混搭（Other）的，确认组合内没有冲突再继续。

## 4. 写文档

- 写入当前项目的 `docs/PRD.md`、`docs/PRD-HUMAN.md`、`docs/ARCHITECTURE.md`，没有 `docs/` 就新建。任一文件已存在时先问：覆盖 / 另存为带日期的新文件（如 `PRD-2026-10-20.md`）/ 取消。
- 结构照本 skill 目录下 `templates/` 里的同名模板。模板里的 `<!-- -->` 注释是写作说明，写完删掉；保留小节编号，与项目无关的小节写「不涉及」加一句原因。
- 只写确认过的内容。假设在正文标「（假设）」，并汇总到 PRD 的「假设」一节；没定的写进「待定问题」，不要自己编。
- 中文，简短，不写"本文档旨在……"这类空话。

**PRD.md 是需求的唯一依据**，pi-forge 用程序读其中三样东西，格式必须照写：

1. 每条需求是一个标题，标题里只带一个编号 `REQ-001`（三位数字，从 001 连续编），例如 `### 3.1 登录  REQ-001`。
2. 验收标准写在该需求下面，每条一行，以 `- AC1` 开头，写成 `Given … When … Then …`，用具体的数据和文案，能直接据此写测试。每条需求至少一条。
3. 「页面」一节的表格，表头是 `页面 | 原型文件 | 对应需求 | 路由`。原型文件写 `docs/prototype/<页面id>.html`，页面 id 用小写英文和连字符（如 `query-list`），原型由 `/ui-prototype` 按这个文件名生成；对应需求写 REQ 编号；路由写前端地址（如 `/queries`、`/queries/:id`）。

另外：

- 页面表之后，每个页面一个小节，写清类型、入口、布局、字段、操作、状态和假数据要求，具体到前端能直接据此搭原型。这些小节的标题不带 REQ 编号，里面不要出现以「- AC」开头的行。
- 「通用约定」一节会原样发给 pi-forge 的开发与审查 agent：写全局的字段规则、格式（时间、金额、分页）、错误提示和权限表现。
- 数据实体只写业务含义（字段、约束、状态流转），表结构、接口由 pi-forge 的架构师定。

**PRD-HUMAN.md** 是给人看的精简版，一到两屏，开头注明「以 PRD.md 为准」。内容和 PRD.md 一致，只是更短：不写验收标准和页面细节。

**ARCHITECTURE.md** 只写技术栈，pi-forge 的架构师照它搭骨架、不自己挑：后端、数据库、前端、测试与检查、运行与部署、必须用与不能用，共六节，最后附选型说明。写清用什么、什么版本；不需要的写「不用」，交给架构师挑的写「由架构师定」。目录结构、数据表、接口不写在这里。

写完后用不超过 5 行汇报：三个文件的路径；需求数、验收标准数、页面数；还剩几条待定问题；下一步运行 `/ui-prototype` 生成前端原型。然后结束。
