# grill-spec

把用户的项目想法变成两份文档：`docs/PRD.md`（做什么）和 `docs/ARCHITECTURE.md`（怎么做）。分四步：拷问 → 确认共识 → 技术选型 → 写文档。每一步等用户回答后再往下走。文档写完就结束，不写代码、不搭原型。

## 0. 开始

- 用户调用时附带了想法，就以它为起点；没有就请用户用一段话描述：想做什么、给谁用、为什么现在做。
- 先自己收集**事实**。当前目录如果是已有项目，读 README、`docs/`、主要代码，了解已有功能、技术栈和约束；`docs/PRD.md` 或 `docs/ARCHITECTURE.md` 已存在时读进来作为输入。能查到的事实不问用户。

## 1. 拷问

把要定的事情看成一棵**决策树**：每个决定下面挂着依赖它的决定。一轮一轮地问：

- 每轮只问**前沿**：前提都已定下、现在就能回答的决定。依赖本轮其他问题答案的，留到下一轮。
- 用 AskUserQuestion 提问，每轮最多 4 题。每题 2–4 个选项，推荐项放第一个、label 末尾加「（推荐）」，description 写清这个选项意味着什么、代价是什么。用户总可以选 Other 自己写。没有 AskUserQuestion 时（如非交互模式），用编号文字列出同样的题目和选项，请用户按「1A 2B」回复。
- 只问**决定**，不问事实。事实自己查；查不到又影响决定的，写进选项（"日活过万选 A，否则选 B"）。
- 每轮提问前用 1–3 行说清上一轮定下了什么、因此冒出了哪些新问题。
- 回答模糊（Other 里写"看情况""都行"）的，下一轮追问到能落地；用户说"你定"的，采用推荐项并记为**假设**。
- 新回答推翻了之前的决定时，指出受影响的已定事项，重新问它们。

要覆盖的分支（大致按这个顺序，按依赖关系调整；与项目无关的分支说一句后跳过）：

1. **问题与目标**：解决谁的什么问题，怎么算成功（可度量的指标）。
2. **用户与角色**：有哪些角色，各自能看什么、做什么。
3. **范围**：本期做什么，明确不做什么。
4. **核心流程**：主流程的每一步，以及异常、失败、取消、空数据时怎样。
5. **页面**：有哪些页面，每页给谁用、放什么、能做哪些操作。
6. **数据**：有哪些实体、关键字段、实体间关系、状态怎么流转。
7. **业务规则**：校验、计算、审批、通知、导入导出、第三方集成。
8. **非功能**：数据量与并发、性能、安全与合规、审计日志、可用性。
9. **约束**：上线时间、团队熟悉的语言和技术、预算、部署环境（公有云 / 内网 / 指定厂商）。第 3 步的选型靠它，必须问到。

所有分支都走过、没有任何事是悄悄假定的，拷问才结束。

## 2. 确认共识

输出一份不超过一屏的摘要：

- 一句话定位
- 已定决策（按上面的分支分组）
- 假设（逐条列出，用户可推翻）
- 明确不做

再用 AskUserQuestion 问「确认，进入选型」还是「需要修改」。要修改就回到第 1 步问相关问题，然后重新确认。

## 3. 技术选型

- **前端固定使用 Strata**（https://github.com/M2tHane/strata-ui）。不读 Strata 的文档，不给前端备选方案。
- 后端给 2–3 套完整组合，每套覆盖：语言与框架、数据库、认证方式、需要时的缓存 / 队列 / 文件存储、部署方式。
- 每套方案都从第 1 步的结论出发说明：为什么适合（对应哪些需求和约束）、优点、代价与风险、运维复杂度、对团队技能的要求。先给一张对比表，再每套写几行，标出推荐方案和理由。
- 不为凑数给明显不合适的方案；只有一种合理选择时直接说明，请用户确认。
- 写具体版本号前先查当前稳定版（用可用的文档或搜索工具）；查不到就只写大版本并标「待确认」。
- 用 AskUserQuestion 让用户选。用户想混搭（Other）的，确认组合内没有冲突再继续。

## 4. 写文档

- 写入当前项目的 `docs/PRD.md` 和 `docs/ARCHITECTURE.md`，没有 `docs/` 就新建。任一文件已存在时先问：覆盖 / 另存为带日期的新文件（如 `PRD-2026-10-20.md`）/ 取消。
- 结构照本 skill 目录下的 `templates/PRD.md` 和 `templates/ARCHITECTURE.md`。模板里的 `<!-- -->` 注释是写作说明，写完删掉；保留小节编号，与项目无关的小节写「不涉及」加一句原因。
- 只写确认过的内容。假设在正文标「（假设）」，并汇总到 PRD 的「假设」一节；没定的写进「待定问题」，不要自己编。
- PRD 的页面级规格要具体到前端能直接据此搭原型：每个页面的字段、操作、状态、假数据要求都写全。
- 两份文档要对得上：PRD 的功能编号（F1…）、页面编号（P1…）、实体名在 ARCHITECTURE 里原样引用；ARCHITECTURE 的路由表覆盖 PRD 的每个页面，接口清单覆盖每个页面需要的读写。
- 中文，简短，不写"本文档旨在……"这类空话。

写完后用不超过 5 行汇报：两个文件的路径；页面数、功能数、实体数；还剩几条待定问题。然后结束。
