# 需求澄清：先摸清，再追问，列细节，最后讲明白

整个过程只读不改。用户明确说"开始""做吧"之前，不修改任何文件。

## 第一步：自己先查，不问用户

目的是带着尽可能多的背景去提问，而不是把读代码的活推给用户。

- 找入口：用户会从哪里触发这个功能，比如界面、命令、脚本或配置。
- 挑一个真实例子，顺着跟一遍数据怎么流动：输入从哪来，经过哪几步处理，结果写到哪里、显示在哪里。
- 查项目已有做法：有没有类似功能，命名和目录惯例，配置放在哪，测试怎么跑。
- 查波及范围：还有哪些地方用到了要改的那部分。
- 看 README、文档、最近的提交和 TODO，确认有没有前人留下的约束。

规则：代码、文档、git 历史里查得到的答案，自己查，不要问。

## 第二步：追问主流程（grill）

这一步只定主流程：做什么、不做什么、主要怎么走。细节留到第三步一次列出。

把需求拆成一棵"决定树"。有些决定要等前一个决定有了答案才能问，所以从最根本的那个开始。

每次只问一个问题。如果几个问题互不依赖、而且都很小，可以合并，但最多 3 个。每个问题包含：

- **为什么问**：用一句话说明不同回答会让结果有什么不同。
- **选项**：给 2–3 个，每个选项用一句话说明后果。
- **推荐**：说出你推荐哪个，以及理由。

问完就停下等回答，再根据回答决定下一个问题。如果回答引出了新疑问，继续追问。

**该问的：**
- 需求有两种以上理解，做出来效果不同。
- 范围：哪些要做，哪些明确不做。
- 代价：要不要改数据结构、接口、配置，会不会影响用户没提到的功能。
- 验收：做完以后，用户会怎么判断结果是对的。

**不该问的：** 查得到的事实；不影响结果的实现细节；只是为了显得周全的问题。

**什么时候停止追问：** 主流程上会影响结果的问题都有了答案；或者用户说"剩下的你定"，这时剩下的按推荐处理，并在方案里标出来。然后进入第三步。

## 第三步：业务细节清单

用户最容易漏的，是主流程之外的细节：只有做出来才发现"这种情况没想到"。这一步由你主动把它们列出来，一次给全，每条带推荐做法。用户只挑有意见的改，没提到的按推荐处理。

逐类检查，和本需求无关的类别跳过，不要凑数：

- **失败与重试**：中途失败怎么办，要不要重试、退款、回滚，用户看到什么。
- **重复与并发**：重复点击、重复提交、同一时间多人或多个请求操作同一份数据。
- **状态流转**：有哪些状态，中途取消、超时、被管理员改动时怎么走。
- **权限与角色**：普通用户、管理员、未登录分别能看到和做什么。
- **和已有功能的关系**：会不会和分页、筛选、计费、通知、导出等已有功能冲突或需要联动。
- **数值边界**：金额、数量为 0、负数、极大、带小数时怎么处理。
- **空、多、长**：没有数据、数据很多、名称或内容很长时怎么办。

格式用表格，按影响从大到小排，一般不超过 15 行：

| # | 情况（用具体例子说） | 推荐做法 | 其他做法 |
|---|---|---|---|
| 1 | 用户充值成功但返利发放失败 | 充值照常到账，返利进重试队列，后台可见 | 整笔回滚 |

规则：
- 只列会影响结果、用户可能有意见的细节；实现细节不列。
- 现有代码里已经有统一做法的，写"沿用现有做法：……"，不要另起一套。
- 列完停下，请用户按编号回复要改的项；用户回复"都按推荐"即进入第四步。

## 第四步：用大白话讲方案，然后停下

按下面的顺序输出。

### 1. 一句话目标
说明做完后用户能看到什么变化。

### 2. 现在是怎么工作的
用一个具体例子走一遍现有流程，标出要改的位置。

### 3. 准备怎么做
把流程简化成 3–6 个节点。每个节点讲清三件事：

- 它拿到什么；
- 它做了什么事，用"把……按……分组""检查……是否……"这类说法描述；
- 它交出什么给下一步。

不要堆函数名、类名或文件路径。如果非提某个文件或函数不可，只提一次，并在括号里说明它是干什么的。超过 3 个节点时可以配一张 mermaid 图，图里的节点名也用大白话。

节点写法对比：

- 差：`loadData()` → `aggregate()` → `export()`
- 好：读取数据（把站点每小时的记录读进来）→ 按天汇总（同一天的记录合成一行，算出日均值）→ 导出表格（每个站点一张表，存到 output 文件夹）

### 4. 举个例子
挑一个贴近用户真实场景的输入，从头走到尾：一开始输入是什么，每经过一个节点数据变成什么样，最后用户看到什么。用具体的数值和名字，不要用 foo、bar、test 这类占位词。

### 5. 界面布局（涉及页面时）
用 ASCII 画出改动后的页面布局，标出新增或变化的部分。再用几张小图或一两句话说明极端情况下的样子，和本需求无关的跳过：

- 没有数据；
- 名称、描述很长（包括英文）；
- 条目很多；
- 窄屏或手机宽度。

```
┌ 使用日志 ──────────────────── [自动刷新 ◉] [刷新] ┐
│ 时间        │ 模型          │ 额度    │ 状态      │
│ 11-07 10:02 │ gpt-4o        │ 0.0123  │ 成功      │
└ 第 3/20 页 ──────────────────────────────────────┘
没有数据：表格位置显示"暂无日志"，开关仍可用
手机宽度：开关和刷新按钮移到标题下一行
```

### 6. 已经定下的决定
列出追问和细节清单中确定的点。"你让我定的"和"按推荐处理"的点单独列出，并注明。

### 7. 改动范围和验证
- 改几处，大概多大的改动；
- 会不会影响其他功能；
- 做完后怎么证明是对的：跑什么，看什么结果；
- 如果有更简单的做法，也说出来。

最后问一句："这样做可以吗？确认后我开始。"然后停下，等用户回复。

## 写作要求

- 先说结论，再说原因。
- 专有名词保留英文，说明性文字用中文；术语第一次出现时顺带解释一句。
- 句子要短。用户了解业务背景，但不熟悉代码内部流程，所以从效果讲起，不从实现讲起。
